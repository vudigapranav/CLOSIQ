# Build and test on Android

Use an ARM64 Android phone, USB debugging, Android SDK and JDK 21. This guide uses a standalone APK with bundled JavaScript so airplane-mode testing does not depend on Metro. The repository includes a Kotlin LiteRT-LM module. Expo Go cannot load it.

## The APK that was built (2026-11-19)

```text
builds/CLOSIQ-V2-2.0.0-arm64-release.apk
60,417,798 bytes, SHA-256 79d40430983c59fc6857379d4af3dcf30ab932e2ba6e8d8a37bd7d09ba90e10e
package com.closiq.app.v2 · versionCode 1 · versionName 2.0.0 · minSdk 24 · targetSdk 36 · arm64-v8a only
```

`builds/` is git-ignored; the file is a local build artifact. Gradle also leaves the same APK at `mobile/android/app/build/outputs/apk/release/app-release.apk` (that folder is regenerated by `npx expo prebuild`).

It is signed with the Expo template's local debug certificate, so it installs by sideload against any other V2 test build, and cannot be uploaded to Play. Production signing is a separate step.

## Shortest physical test (from the phone + this Mac)

```sh
cd /Users/pranav07vudiga/Desktop/Projects/Hackathon/Demux/CLOSIQ/CLOSIQ-v2
adb devices -l                       # the phone must appear as 'device', not 'unauthorized'
adb install -r builds/CLOSIQ-V2-2.0.0-arm64-release.apk
```

On the phone:

1. Open **CLOSIQ V2** and finish onboarding as a guest (no account, no network needed). V1 stays installed and untouched — a different application ID.
2. **Profile → Manage local AI → Download model.** This is the only model download and it needs Wi-Fi once. Expect 363,085,824 bytes; the app checks the byte count and the SHA-256 (`7b432bbc…f74e`) natively before the file is renamed into its private no-backup folder.
3. Tap **Load model**, wait for the status to become *ready*, then turn on **airplane mode** and disable Wi-Fi.
4. Tap **Test a garment photo on Android**, pick a real garment photo already on the phone, and copy the three numbers it prints: **Init**, **Inference**, **PSS**. Repeat with the **Benchmark with GPU** switch on the same photo (some phones only have a usable CPU path).
5. Force-stop and reopen CLOSIQ while still offline: add a different photo, correct the attributes, save it, generate a look, swap one item, save the look, add a planner entry, then force-stop and reopen again. Photos and records must all still be there.
6. **Profile → Export wardrobe and photos**, then restore that folder into a fresh V2 install to prove backup/restore.

Record: phone model, SoC, Android version, RAM, ABI, free space, backend (CPU/GPU), and the exact text the model returned for the photo.

## Rebuilding from source

```sh
cd /Users/pranav07vudiga/Desktop/Projects/Hackathon/Demux/CLOSIQ/CLOSIQ-v2/mobile
npm ci
npm run check:release-env
ANDROID_HOME=$HOME/Library/Android/sdk npx expo prebuild --platform android --no-install --template ./node_modules/expo/template.tgz
GRADLE_USER_HOME=$PWD/.gradle-home ANDROID_HOME=$HOME/Library/Android/sdk \
  ./android/gradlew -p android -Dorg.gradle.jvmargs="-Xmx6g -XX:MaxMetaspaceSize=1536m" \
  :app:assembleRelease -PreactNativeArchitectures=arm64-v8a \
  -Pkotlin.compiler.execution.strategy=in-process --max-workers=4
```

Three details are load-bearing and are already handled by the checked-in config plugin `mobile/plugins/with-android-build-compat.js`:

- **NDK / Build Tools.** Expo prefers NDK 27.x and Build Tools 35.0.0. If those are not installed, Gradle fails with `NDK not configured` or `Failed to find Build Tools revision 35.0.0`. The plugin points both at the newest installed versions (here NDK 28.2.13676358, Build Tools 36.1.0). Override with `CLOSIQ_NDK_VERSION` / `CLOSIQ_BUILD_TOOLS_VERSION`.
- **Kotlin metadata.** `com.google.ai.edge.litertlm:litertlm-android:0.19.1` ships Kotlin 2.4 metadata while Expo 57 compiles with Kotlin 2.1.20. The plugin lets the Kotlin compiler accept that newer metadata app-wide; the 2.4 stdlib is what ships in the APK anyway. Remove the flag once the toolchain moves to Kotlin 2.4+.
- **Gradle home.** Set `GRADLE_USER_HOME` if `~/.gradle` is not writable on the build host; the first build then downloads Gradle 9.3.1 and all dependencies (about 2 GB), so allow for that in disk space. `kotlin.compiler.execution.strategy=in-process` avoids a Kotlin daemon that a restricted host cannot start.

First-time dependency resolution needs internet access to Google Maven, Maven Central and the Android build repositories. Core use needs no API key.

## Device test protocol details

1. Open CLOSIQ V2 and complete local onboarding. Manual wardrobe entry is available immediately.
2. Open **Profile → Manage local AI → Download model**. Wait for checksum verification, then tap **Load model**.
3. Enable airplane mode, disable Wi-Fi, and choose **Test a garment photo on Android**. Use a photo already on the phone. Check the actual description, initialization time, inference time and process PSS. Repeat with the GPU benchmark switch on the same photograph. Some devices support only the CPU path.
4. Force-stop and reopen CLOSIQ while still offline. Add a different photo, correct attributes, save it, generate a look and swap one item. Confirm all pieces are in the active wardrobe.
5. Save the look and a planner entry, restart, and verify both photos and records. Use **Export wardrobe and photos**, then restore into a fresh V2 test install on a spare device. Keep V1 installed.
6. Test model cancellation, low space, interrupted download, replacement, deletion and reinstall. Record phone model, SoC, Android version, RAM, ABI, free space, backend and model revision.

For peak memory rather than the point-in-time PSS the app prints: `adb shell dumpsys meminfo com.closiq.app.v2`.

If the native module reports unsupported, rebuild the native app and check Expo autolinking (`npx expo-modules-autolinking search --platform android` must list `closiq-vision`). If a model load fails, keep the exact Android version, error and selected backend. Offline fallback and manual entry should remain usable.
